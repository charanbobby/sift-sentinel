## Wins worth highlighting in submission

### 1. Named-pipe-beacon rule fires on a real attack, not just synthetic plants

`srl-2018-base-wkstn-05` correctly emitted `tbbd05` as `attacker_persistence HIGH` with citation:

> Service `tbbd05` uses the classic named-pipe-beacon command shape: `%COMSPEC% /c echo <hex-token> > \\.\pipe\<number>`. This is the documented artifact of Metasploit's `psexec`, Impacket's `smbexec`, and Cobalt Strike's `psexec_psh` lateral-movement modules.

This validates that the prompt rule shipped this morning (commit 4e66654) generalises beyond the synthetic-loop test case.

### 2. Masquerade rule fires consistently across hosts

`base-file` and `base-rd-02` both surfaced `msadvapi2_32.exe` and `msadvapi2_64.exe` under `Microsoft Advanced API 32/64`. The masquerade-counter-rule correctly identifies fake-Microsoft naming conventions across hosts that share an attacker campaign.

### 3. Negative control behaves correctly

`base-dc` returned `NOT_FOUND legitimate_windows_default` HIGH with explicit rule-out of:
- F-Response (`subject_srv.exe` connecting to `base-hunt.shieldbase.lan:5682`)
- Mnemosyne (kernel-mode memory acquisition driver)
- VMware tools, McAfee, all standard Windows components

The agent confidence was MEDIUM rather than HIGH because two regripper steps returned `parse_error`, leaving WDigest and Winlogon vectors unverified. That is an honest hedge.

### 4. dmz-ftp surfaces classic post-exploit artifacts

Two MEDIUM findings, both real attacker patterns:
- `%SystemRoot%\PSEXESVC.exe` (PsExec service binary dropped to SystemRoot, T1543.003)
- `IFEO Debugger` value set to `C:\Windows\System32\cmd.exe` (Image File Execution Options hijack, T1546.012)

Classified as `requires_disambiguation` rather than `attacker_persistence` because PSEXESVC alone could be admin-installed; IFEO with cmd.exe debugger is suspicious but rare in legitimate use. The MEDIUM call is appropriate.

## Gaps the sweep exposed

### G1. wkstn-01 false negative (CONFIRMED by project owner)

The agent emitted `NOT_FOUND HIGH` for `srl-2018-base-wkstn-01`. Project owner confirmed the host was compromised in the SRL-2018 exercise. Three plausible root causes (in order of likelihood, to verify):

1. **Two regripper steps `parse_error`-ed** on this host: `securityproviders` (WDigest credential-theft hint) and `winlogon_tln` (Userinit/Shell hijack). Attackers commonly plant in these registry locations. Until the parse path is hardened, persistence here is invisible.
2. **Three `scheduled_tasks_parse` calls returned 0 entries.** Either `nth_file_inode` resolved to wrong inodes, or the host genuinely has no tasks under `Windows\System32\Tasks\` (unusual). Need to inspect step-19 fls_list output for the Tasks dir.
3. **Memory-only persistence.** wkstn-01 has a matching `base-wkstn-01-mem.zip` that has never been run through the memory channel. Could be process injection, in-memory implants.

The agent's confidence was HIGH despite (1) and (2) leaving real gaps. R_15 LOW_CONFIDENCE_AUTO_ESCALATE only escalates LOW, so a HIGH NOT_FOUND with parse_errors slips through. Worth raising the bar: NOT_FOUND should require **all** primary steps to complete cleanly, not just be free of attacker_persistence emissions.

### G2. Confidence calibration on parse_error

`base-dc` correctly hedged to MEDIUM under parse_errors. `base-wkstn-01` did not. Same gap, different output. Suggests the LLM's hedging is inconsistent and needs a deterministic rule rather than relying on judgment.

### G3. DFIR-tool findings not suppressed at scoring

Both `rd-01` and `wkstn-05` emitted F-Response and Mnemosyne as `legitimate_responder_tool HIGH`. The pipeline counts them in `findings.json`. Per the prompt rules these should be suppressed at output, not emitted. The score script likely already filters them, but it inflates the visible finding-count number.

## Suggested follow-ups (post-submission)

1. **Owner-annotate `base-file`, `rd-01`, `rd-02`, `dmz-ftp`** so they move from sampled-review to GT-scored.
2. **Investigate wkstn-01 parse_errors.** Pull the actual SOFTWARE/SYSTEM hives off this host and run regripper outside the pipeline; compare to determine whether the data exists on disk and the parser is dropping it, vs the data not being present.
3. **Tighten R_15 / NOT_FOUND emission rule.** When any primary step returns `parse_error`, NOT_FOUND should not be HIGH; downgrade to MEDIUM at minimum, possibly LOW (which auto-escalates).
